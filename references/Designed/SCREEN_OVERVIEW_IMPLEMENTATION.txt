===============================================================================
0. PURPOSE OF THIS FILE
===============================================================================

This file defines how Codex should assemble the approved Games / Overview screen.

This is NOT a request to redesign the screen.
This is NOT a request to change the site architecture.
This is NOT a request to replace working functionality.

The task is to reproduce the approved visual direction inside the existing site,
preserving the current routing, data, project media, carousel behavior, responsive
logic, links, and content relationships.

Future screen implementation TXT files will reference the SAME shared component
and asset nomenclature established here. Reuse existing named components/assets
instead of creating screen-specific duplicates whenever the visual function is
the same.

If an approved Overview mockup image is present in the repository, use it as the
primary visual reference together with this specification. Where the mockup and
this file differ, follow explicit instructions in this file.


===============================================================================
1. GLOBAL DESIGN RULE
===============================================================================

North-star:
    GUILTY GEAR INTENSITY + NINTENDO-LIKE CLARITY / TACTILITY

Interpret this as:
- aggressive, authored visual identity around the interface
- clean, readable functional interiors
- strong hierarchy
- chunky, obvious clickable elements
- tactile depth
- clear selected / unselected states
- restrained but deliberate use of red
- game-interface personality without becoming noisy

Core principle:
    EXPRESSIVE SHELL -> DISCIPLINED INTERFACE

Do NOT:
- redesign the site navigation architecture
- make this look like a conventional corporate portfolio
- copy Nintendo / Smash / Guilty Gear proprietary UI
- rasterize ordinary buttons, panels, borders, shadows, tabs, or clipped corners
- bake text into decorative assets
- cover body copy with grunge
- add unnecessary icons
- make every surface red
- make containers overly transparent
- restore duplicate carousel counters / controls removed in the approved design

2.5 BUTTON FAMILY
------------------------------------------------------------------------------

BASE COMPONENT: ui-btn

Variants:
    ui-btn--primary
    ui-btn--secondary
    ui-btn--compact
    ui-btn--carousel
    ui-btn--nav

Suggested structure:
    .ui-btn
    .ui-btn__label
    .ui-btn__icon

State modifiers:
    .is-hover
    .is-focus
    .is-pressed
    .is-selected
    .is-disabled

Interaction philosophy:
REST:
    clear light surface + restrained shadow
HOVER:
    slight lift OR slightly stronger shadow / exposed red accent
FOCUS:
    obvious keyboard-visible focus treatment
PRESSED:
    slight physical compression / reduced shadow offset
SELECTED:
    persistent red emphasis / stronger framing where relevant
DISABLED:
    reduced contrast but readable

Implementation:
    HTML/CSS + SVG/icon font/plain text arrow where appropriate

Do NOT rasterize buttons.

===============================================================================
9. DEPTH / MATERIAL LANGUAGE
===============================================================================

This is a CRITICAL change from the earlier implementation.

Cards and controls should NOT look like transparent boxes floating over paper.

Preferred depth:
- warm off-white / light opaque fill
- dark 1-2px-ish outline depending on scale
- compact dark shadow or offset
- optional narrow red underslab
- shadow should communicate tactility, not float dramatically
- consistent depth direction across components

Avoid:
- glassmorphism
- translucent gray cards
- huge blurred drop shadows
- soft corporate card styling
- large elevation differences between ordinary controls


===============================================================================
10. TYPOGRAPHY
===============================================================================

Preserve the existing strong condensed display identity.

Hierarchy:
PAGE TITLE:
    largest, bold, condensed, cream on black plate

SECTION TITLE:
    large condensed, cream on red plate

CARD TITLES:
    bold condensed, dark text

BODY:
    highly legible, comparatively neutral
    do not distress body copy

EYEBROWS / LABELS:
    uppercase
    red or dark depending on background
    compact tracking acceptable

Avoid tiny body text.
Do not let stylistic fonts hurt readability.

===============================================================================
12. RESPONSIVE RULES
===============================================================================

Desktop:
    composed interface

Tablet / mobile:
    normal responsive scrolling document

Canonical desktop should preserve:
- left rail
- central composed content
- right identity rail
- 3-across role cards
- horizontal project showcase

As width decreases:
1. protect readable text first
2. allow content area to scroll vertically
3. role cards may collapse to 2 columns then 1
4. project showcase may stack media above info
5. carousel arrows must remain reachable and not obscure content
6. numbered project tabs remain accessible
7. do not force the desktop composition into an unusable narrow viewport

Do not redesign mobile into a separate visual language.


===============================================================================
13. ACCESSIBILITY / INTERACTION REQUIREMENTS
===============================================================================

All clickable controls:
- use semantic links/buttons
- keyboard operable
- visible focus state
- sufficient hit area
- no interaction that depends exclusively on hover

Carousel:
- arrow buttons need aria-labels
- numbered tabs should expose current selection with aria-current or equivalent
- do not remove current project information from screen readers during visual
  transitions without a replacement accessible state

Contrast:
- preserve strong text/background contrast
- selected red states must remain readable

Motion:
- keep transitions short
- honor prefers-reduced-motion if the project already supports it or can do so
  cheaply

20. FINAL IMPLEMENTATION INTENT
===============================================================================
