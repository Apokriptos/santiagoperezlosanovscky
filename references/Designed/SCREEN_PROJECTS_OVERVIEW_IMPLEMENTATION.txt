2. SCREEN PURPOSE
===============================================================================

This screen is the PROJECTS OVERVIEW.

Its purpose is to:
- present the three primary projects immediately
- make project identity strongly visual
- let the user enter any project directly
- preserve the contextual right-side project index
- serve as the visual gateway into project detail pages

This screen is NOT:
- the general Games landing page
- a case study hub
- an About Me page
- a long project description page
- a video overview page

Do NOT add Case Studies or About Me shortcut panels here.

===============================================================================
9. PROJECT CARD GEOMETRY
===============================================================================

Each card should use the shared surface/depth language but be more expressive
than ordinary role cards.

Visual grammar:
- slight individual rotation / skew is acceptable
- controlled irregularity
- strong straight edges remain dominant
- no excessive polygon complexity
- one or two clipped corners maximum
- outer white/cream edge
- black outline
- compact black shadow
- thin red offset/underslab as accent
- project image framed cleanly

Suggested desktop styling:
- cards approximately equal width
- center card may sit slightly differently in angle than left/right
- cards visually overlap the expressive background without overlapping each other
- maintain readable spacing between cards

The differences in angle should feel authored, not random.

Implement rotation/skew via CSS transforms, not rasterized frames.

===============================================================================
11. PROJECT CTA
===============================================================================

Use the shared button/control language.

Suggested:
    project-card__cta
    built from ui-btn principles

Visual:
- compact square/angled arrow control
- strong contrast
- red variant for emphasized/selected project
- light variant for ordinary card
- physically integrated into title band

Behavior:
Preferred:
    entire project-card is clickable

The arrow should reinforce affordance, not be the only clickable area.

If whole-card linking conflicts with nested interactive semantics, use a single
stretched-link pattern or equivalent clean implementation.

Accessibility:
- semantic anchor
- visible keyboard focus
- aria-label where needed
- avoid nested anchors/buttons


===============================================================================
12. CARD INTERACTION
===============================================================================

REST:
- compact shadow
- strong frame
- no unnecessary animation

HOVER:
- slight lift / translateY
- tiny increase in rotation confidence or reduced paper contact
- shadow becomes slightly more visible
- red accent may expose slightly more
- CTA may shift a few pixels or strengthen contrast

FOCUS:
- visible focus ring/frame that fits the existing visual system

PRESSED:
- slight compression
- reduced shadow offset

Selected/current:
- only use selected state where meaningful
- do not make unselected cards appear unavailable

Motion:
- short and tactile
- no long cinematic transitions
- respect prefers-reduced-motion
